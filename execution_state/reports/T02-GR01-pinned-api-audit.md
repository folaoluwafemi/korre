# T02-GR01 pinned API audit

## Scope and source provenance

This was a read-only inspection of the package sources already present in `node_modules/.pnpm`; nothing was installed or fetched. The installed package metadata reports `@babylonjs/core` **9.30.0** and `@babylonjs/havok` **1.3.14**, matching the requested pins. The declarations and JavaScript implementation cited below are from those exact package roots.

## Shape geometry

Babylon exposes the shape kind through `PhysicsShape.type` and exposes `getBoundingBox()` in [`physicsShape.d.ts`](../../node_modules/.pnpm/@babylonjs+core@9.30.0/node_modules/@babylonjs/core/Physics/v2/physicsShape.d.ts:63) and `:156`. The constructor declarations are concrete: `PhysicsShapeCylinder(pointA, pointB, radius, scene)` at `:205-213` and `PhysicsShapeBox(center, rotation, extents, scene)` at `:225-233`. The generic `PhysicsShapeParameters` declaration in `Physics/v2/IPhysicsEnginePlugin.d.ts:178-204` names `radius`, `pointA`, `pointB`, `rotation`, and `extents`.

The Babylon `PhysicsShape` object does **not** declare a public `parameters` getter or public radius/height members. Its `_pluginData` is declared `any` at `physicsShape.d.ts:32-42`; this is plugin storage, not a typed geometry-inspection API. In the pinned Havok plugin implementation, `getBoundingBox(shape)` calls `HP_Shape_GetBoundingBox` at the identity transform (`Plugins/havokPlugin.js:1764-1771`), so the result is a local, axis-aligned bounding box, not an exact primitive-parameter readback. `getBodyBoundingBox(body)` transforms that AABB by the node world matrix (`:1784-1788`); it describes the current pose only.

The raw Havok declarations can create cylinders and boxes from exact constructor arguments (`HavokPhysics.d.ts:252` `HP_Shape_CreateCylinder`, `:257` `HP_Shape_CreateBox`), report an AABB for a supplied single `QTransform` (`:295` `HP_Shape_GetBoundingBox`), report shape kind (`:293` `HP_Shape_GetType`), and build mass properties (`:299` `HP_Shape_BuildMassProperties`). They do not declare a getter that returns a cylinder's original radius/endpoints. Therefore, for this game, exact cylinder geometry should come from the canonical config and the owned `worldFactory` construction arguments, with the shape type checked at runtime; the package does not provide an independent exact parameter readback. Do not infer exact radius and height from a rotated AABB.

The current factory uses the direct cylinder constructor with the configured radius and vertical endpoints for caps/buttons (`games/counterball/src/simulation/worldFactory.ts:303-311`), and direct configured `PhysicsShapeBox` dimensions for the slab (`:214-224`). This is a traceable source-of-truth construction, not a runtime introspection result.

## Current mass and inertia

The supported Babylon entry is `PhysicsBody.getMassProperties(instanceIndex?)`, declared at `physicsBody.d.ts:189-198`; `computeMassProperties()` is separately declared at `:168-177`. The distinction matters in the pinned Havok implementation:

- `HavokPlugin.getMassProperties(body, instanceIndex?)` is declared at `Plugins/havokPlugin.d.ts:422-427`. Its implementation calls `HP_Body_GetMassProperties` on the body's native Havok handle and converts the returned tuple (`Plugins/havokPlugin.js:1133-1137`). This is the readback of the mass properties currently configured on the native body.
- `computeMassProperties()` instead rebuilds properties from the shape through `HP_Body_GetShape` and `HP_Shape_BuildMassProperties` (`Plugins/havokPlugin.js:1087-1108`). On a failed native shape/mass query, the implementation silently uses a unit-mass/unit-inertia fallback (`:1095-1096`); it is not evidence of the body's current effective values.
- `setMassProperties()` records the user overrides and sends the merged tuple through `HP_Body_SetMassProperties` (`Plugins/havokPlugin.js:1007-1024`, `:1121-1125`). Reading back after setting is the right way to verify the actual native state.

The Babylon `PhysicsMassProperties` declaration (`Physics/v2/IPhysicsEnginePlugin.d.ts:286-320`) defines `mass`, local-space `centerOfMass`, `inertia`, and `inertiaOrientation`; its `inertia` documentation describes principal moments for **unit mass**. Havok's native `MassProperties` tuple independently states `[center of mass, Mass, Inertia for mass of 1, Inertia Orientation]` (`HavokPhysics.d.ts:110-115`). Thus the returned native tuple contains actual configured mass plus principal unit-mass moments and their orientation. For physical energy/inertia calculations, account for this documented unit-mass convention; do not silently treat the vector as already multiplied by mass. Check the returned values and orientation for finite values, and require positive finite mass and positive usable principal moments before dividing by them.

The high-level wrapper indexes element 1 of `HP_Body_GetMassProperties` without exposing/checking its native result code (`havokPlugin.js:1133-1136`). A strict caller can reject malformed/non-finite returned values, but cannot observe that low-level status through `PhysicsBody.getMassProperties()` alone. The body plugin handle is internal (`PhysicsBody._pluginData`); directly calling `HP_Body_GetMassProperties` requires reaching into implementation storage. That raw route should not become production coupling unless the adapter deliberately owns and types it.

`PhysicsBody.getLinearVelocity()` and `getAngularVelocity()` are public (`physicsBody.d.ts:269`, `:297`). They provide useful sampled pre-step state; the native declaration also has atomic `HP_Body_GetQTransform(bodyId)` at `HavokPhysics.d.ts:356`. The latter requires a native ID not exposed as a typed public body property.

## Motion, shape casts, and support bounds

The Babylon query `IPhysicsShapeCastQuery` is declared in `Physics/physicsShapeCastQuery.d.ts:7-31`. It supplies one `rotation`, a `startPosition`, and an `endPosition`, plus trigger/body filtering. The public Havok plugin method `shapeCast(...)` is declared at `Plugins/havokPlugin.d.ts:957-962`; the implementation forwards that single orientation and the two positions to `HP_World_ShapeCastWithCollector` (`Plugins/havokPlugin.js:2389-2415`). The raw `ShapeCastInput` has exactly one shape orientation and linear start/end positions (`HavokPhysics.d.ts:180-187`); the result gives a hit fraction and contact points (`:189-193`). This is a translational cast at fixed orientation, not an angular/rotational sweep. The pinned declarations expose no cast whose input describes a continuously rotating cylinder.

`PhysicsShape.getBoundingBox()` and `PhysicsBody.getBoundingBox()` are pose/AABB queries; neither gives a swept bound. Havok's `HP_Shape_GetBoundingBox(shape, worldFromShape)` also accepts only one transform (`HavokPhysics.d.ts:295`). `PhysicsEngine.setSubTimeStep()` exists (`physicsEngine.d.ts:56-66`), but it does not expose intermediate transforms or a per-substep sweep certificate. The pinned `HavokPlugin.executeStep(delta, bodies)` implementation calls `HP_World_SetIdealStepTime` and then one `HP_World_Step` for each region (`Plugins/havokPlugin.js:600-605`); the ideal time call is solver configuration, not a continuous-motion query.

There is still a conservative *geometric envelope* that the adapter can calculate before a step when it owns the constructor geometry and validates the native mass readback. For a cylinder of radius `r`, endpoint separation/height `h`, and COM offset magnitude `c` from its geometric center, a safe rotation-independent radius is `rMax = c + sqrt(r² + (h/2)²)`. Given a valid whole-interval center-speed bound `vBound` and angular-speed bound `omegaBound`, every collider point travels at most `(vBound + omegaBound*rMax)*dt` in that interval. A sphere centered on the pre-step COM with radius `rMax + vBound*dt` contains the entire collider throughout translation and arbitrary rotation; a tighter point-sweep distance may use the angular term as well. That envelope can be checked against the configured open support region and slab extents before taking the step. It is conservative and may reject safe trajectories.

**Conclusion: the pinned APIs alone do not prove the actual full swept cylinder path/support bound before a Havok step.** They provide current transforms/velocities, current native mass properties, constructor geometry known to the adapter, current-pose AABBs, and fixed-orientation linear casts. They do not expose the integrator's continuous path, angular cast, internal solver trajectory, or a documented guarantee that an externally derived energy/speed ceiling bounds every internal numerical pose during `HP_World_Step`. The contract's energy and per-point speed equations can support a conditional mathematical envelope, but that relies on the game-level passivity/energy assumptions and on the selected bounds being enforced. A post-step energy observation can detect an observed violation; it cannot retroactively prove that no transient support crossing happened inside that step.

Accordingly, a runner can honestly claim a **pre-step conservative guard conditional on the documented energy and geometry envelope** if it: uses exact immutable factory geometry; reads and validates the current native mass properties; derives finite `vBound`, `omegaBound`, and `rMax`; bounds the entire candidate substep with a rotation-independent collider envelope (or a separately proven rotational support function); checks the complete envelope against horizontal support and vertical slab constraints; and fails closed before the step if any input, limit, or query is unavailable. It must still describe real Havok non-tunnelling as unproven by the API alone until hosted real-WASM trials provide evidence. A fixed-orientation shape cast or endpoint-only bounding box is not sufficient for the claimed rotational sweep.

## Checks and limits

This task used only read-only inspection of installed `package.json`, `.d.ts`, and package `.js` sources. No install, application build, test, lint, browser, physics run, or deployment was performed. This report audits API capability; it does not prove an implementation guard, solver passivity, no tunnelling, deployed Havok behavior, or gameplay calibration.
