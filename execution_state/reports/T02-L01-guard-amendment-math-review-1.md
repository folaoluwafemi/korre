## Source and arithmetic findings

The conditional energy calculation is correct: a centered magnitude-8 impulse on a mass-1 cap at rest contributes 32 energy units; the maximum stated drop for total dynamic mass 14.15 at gravity 9.81 contributes 1.561629375; the sum is 33.561629375, which rounds up to 34 with 0.438370625 headroom. The corresponding magnitude-6 total is 19.561629375. The report correctly does not treat the headroom as solver-passivity proof and correctly calls out that an off-center impulse, nonzero initial velocity, or another force invalidates this shortcut. See [the math report](execution_state/reports/T02-L01-guard-amendment-math-1.md:21) and the configured masses, gravity, and geometry in [config.ts](packages/game-protocol/src/config.ts:13).

The ideal-cylinder inertia and sweep estimates also check out to the stated precision: cap minimum inertia 0.0268 and farthest radius about 0.3255764; button minimum inertia 0.0006590625 and farthest radius about 0.1319327. At E=34, the button’s combined linear-plus-angular point bound requires 48 calls at 1/120 second for a 0.01125 point-sweep cap, leaving only about 0.000196 of estimated sweep margin. The 325 apron estimate follows from the assumed 15-second reach bound and button radius. These are conditional estimates: the report appropriately requires native mass/inertia, shape, material, pose, and observed-energy checks before relying on them. C00-B supplies the general envelope/formula and schema bounds, not these L01 settings ([CONTRACT_WORK.md](knowledge_base/execution/completion/CONTRACT_WORK.md:67), [CONTRACTS.md](knowledge_base/execution/CONTRACTS.md:135)).

The existing accepted `diagnosticGuard` cannot be reused for L01. Its strict identity is exactly `browser-direct-impulse-v1` for the D01 at-rest `home-6` impulse and application point; the contract excludes restart placement and alternative inputs. Current types and schema expose only that D01 guard, and `physicsCalibration` remains null ([CONTRACTS.md](knowledge_base/execution/CONTRACTS.md:320), [types.ts](packages/game-protocol/src/types.ts:370), [schemas.ts](packages/game-protocol/src/schemas.ts:67)). The canonical hash covers the complete config object ([config.ts](packages/game-protocol/src/config.ts:230), [config.ts](packages/game-protocol/src/config.ts:247)); therefore a separate strict `restartLoftDiagnosticGuard` field can be bound into that hash while leaving the D01 field unchanged. The report is right to require coordinated config/type/schema/fixture/version updates. No wire-message change is proposed, so a protocol-version bump does not follow from the reviewed sources alone.

## Unfrozen assumptions and execution boundary

The proposal correctly identifies remaining decisions. The packet fixes the matrix but does not fully define each constructed state, selected cap and obstacle, how azimuth relates to the impulse direction, the impulse vector and application point, per-case rest-height reference, matrix-wide wall/call/yield budgets, cancellation semantics, or artifact byte/contact limits. The existing `intendedShotProbe.test.ts` shows one possible setup—`home-0`, `home-1`, zero velocities and a centered +z impulse—but it is precedent, not an accepted L01 setup contract ([intendedShotProbe.test.ts](games/counterball/src/simulation/intendedShotProbe.test.ts:128), [intendedShotProbe.test.ts](games/counterball/src/simulation/intendedShotProbe.test.ts:399)). Those assumptions must be explicitly frozen and checked; they cannot be silently inherited from that probe.

Accordingly, the report’s answer to the safety question is sound: **it does not authorize trials.** First accept the L01-specific hashed identity and numeric/workload/output limits, then implement fail-closed preflight and per-call checks. Only the required hosted real-WASM run and artifact review can establish the packet’s runtime evidence. **Runtime and physics were not run locally for this review.**
