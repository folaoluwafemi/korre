## Required changes

1. **[P1] Require the accepted case/output schema before returning success.** `LoftCoarseJsonValue` permits any JSON value for every body/contact/sweep row, `LoftCoarseCaseMetadata` requires only the tuple, index and three counters, and `LoftCoarseMatrixMetadata` is any JSON object (`games/counterball/src/simulation/loftCoarseProbe.ts:28-55`). `assertCaseShape` checks only that the outer value, metadata and row arrays have generic shapes; `writeCase` checks the tuple/index/counters and serializes any JSON rows (`loftCoarseProbe.ts:345-360`, `:367-445`). Thus a 24-case stream with incomplete provenance metadata and rows such as `null` can still produce a success summary. The contract requires the full endpoint/contact/sweep row contents and the extensive per-case provenance/native/material/settling inventory (`knowledge_base/execution/completion/CONTRACT_WORK.md:180-182`). The current test helper itself supplies only five metadata fields and a partial body row (`games/counterball/src/simulation/loftCoarseProbe.test.ts:12-30`), and no test asserts rejection of missing required fields. Define the accepted row and metadata shapes and validate required fields before success, or establish and test an explicit contract-aware validation boundary in this serializer. Keep arbitrary extra JSON handling only where the accepted schema allows it.

2. **[P2] Add tests for reachable row-count and workload boundaries.** The source enforces per-case body/contact/sweep counts and aggregate call/batch/time totals (`loftCoarseProbe.ts:392-400`, `:531-543`), but tests cover exact/over UTF-8 row and metadata byte limits only (`games/counterball/src/simulation/loftCoarseProbe.test.ts:206-271`). Test data uses one call, one batch and one millisecond per case (`loftCoarseProbe.test.ts:12-24`) and never reaches the row-count or workload limits. Add exact-limit and limit-plus-one tests for the reachable per-case count/workload guards, and exact aggregate totals where those totals are reachable. The contract and test acceptance specifically require exact-boundary/over-boundary behavior (`CONTRACT_WORK.md:145-146`; packet acceptance). The implementation report's separate case/matrix byte-cap reachability note is mathematically sound: the accepted row/count ceilings cap a complete case, including JSON framing, below 20 MiB; even 24 complete 20-MiB cases plus both 64-KiB metadata objects and framing remain below 504,365,056 bytes (`CONTRACT_WORK.md:184`). Those two byte thresholds cannot be reached by a valid input while the stricter caps hold, so their untested exact thresholds are not the blocker.

3. **[P1] Make cancellation interrupt an in-flight sink write.** `JsonChunkWriter.flush` checks cancellation before the write and then directly awaits `sink.write(chunk)` (`loftCoarseProbe.ts:336-342`). If the signal becomes aborted while that promise is pending, the writer cannot call `sink.abort` or reject until the write settles; a stuck write can therefore prevent cancellation cleanup indefinitely. The current cancellation test flips `signal.aborted` synchronously inside `write`, then relies on the next writer operation to notice (`loftCoarseProbe.test.ts:357-378`); it does not cover cancellation while backpressure is unresolved. Make cancellation observable during the pending write and add a deferred-write test that aborts before releasing the write, then verifies prompt rejection, sink abort, and no success result.
