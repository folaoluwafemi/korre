## Contract and API findings

`PACKETS.md:25-26` classifies T02-L01 as a worker card under T02 and shows C00 among its dependencies; T02-L02 depends on L01. In `CONTRACTS.md:320-363`, C00 identifies `browser-direct-impulse-v1`, binds it to the exact home-6 D01 fixture, impulse, and application point, says restart placement and other fixture/input changes are outside scope, and requires the guard to be strict and included in the canonical config hash. Its energy and support values are therefore not general authorization for L01. A restart-specific energy/start-state bound and hashed identity must be selected and accepted by the coordinator before L01 trials proceed.

The pinned package API claims checked here match the cited declarations and implementation. In core 9.30.0, `PhysicsBody.shape` has a public getter/setter (`Physics/v2/physicsBody.d.ts:109-119`), `PhysicsShapeBox` has a public constructor (`Physics/v2/physicsShape.d.ts:225-233`), the engine exposes `getBodies()` (`Physics/v2/physicsEngine.d.ts:108`), and the Havok plugin exposes `executeStep(delta, bodies)` (`Physics/v2/Plugins/havokPlugin.d.ts:240`). The pinned implementation calls `HP_World_SetIdealStepTime` and `HP_World_Step` in the world-region loop (`havokPlugin.js:578-608`). Havok documents the ideal-step setting as the intended interval used to adjust solver parameters, and separately documents `HP_World_Step` as the operation that advances the world (`HavokPhysics.d.ts:523-528`); this is not a public guarantee of internal substepping. One caveat: one `executeStep` invocation can call the low-level step once per active world region, so evidence should distinguish counted public calls from low-level region calls.

The public body API exposes mass properties, linear/angular velocity, and collision observables (`physicsBody.d.ts:198, 269, 297, 349`). The Havok plugin’s `getMassProperties` directly takes tuple element `[1]` from `HP_Body_GetMassProperties` and converts it (`havokPlugin.js:1133-1136`), without checking the result-status tuple member. The pinned Havok declaration labels the inertia vector as “Inertia for mass of 1” (`HavokPhysics.d.ts:110-115`), supporting the audit’s warning to apply the mass factor. Thus validation must reject invalid or unavailable native values; the wrapper does not provide the omitted status to the caller.

The shape material getter delegates to the pinned plugin (`physicsShape.d.ts:108-113`; `havokPlugin.js:1656-1664`), and the public API exposes shape type and collision masks (`physicsShape.d.ts:68, 87-103`). The audit’s readback claim is supported. The box/shape setter declarations show a possible isolated diagnostic replacement path, but they do not by themselves prove material/filter preservation, transform equivalence, or disposal ordering at runtime. The report correctly treats those as requirements and does not claim the replacement has been exercised.

The continuous-traversal limitation is also supported. Babylon’s shape-cast query contains one rotation plus start and end positions (`Physics/physicsShapeCastQuery.d.ts:7-23`), and its Havok implementation passes that single rotation and linear endpoints to Havok (`havokPlugin.js:2390-2410`). Havok’s `ShapeCastInput` likewise has a single orientation and two endpoints (`HavokPhysics.d.ts:180-187`). Its shape-AABB function takes one `worldFromShape` transform (`HavokPhysics.d.ts:294-295`). These surfaces cannot certify a rotating cylinder’s full trajectory between observed transforms. Calling the proposed energy-derived point/rotation checks conditional per-call conservative bounds, while keeping continuous traversal unproven, is appropriately limited.

## Coordinator prerequisite and evidence limit

Adding an L01-specific hashed guard is not within the worker’s authority to change shared config or C00. The audit’s proposed coordinator-owned amendment is appropriate: define a distinct strict diagnostic scope bound to L01’s exact matrix/setup, derive and review its energy and sweep/work limits, update the shared config schema and hash fixtures, and revise the accepted contract and task packet/dependencies before dispatch. The config/schema version may need to advance; C00 explicitly keeps wire protocol version 1 when only configuration changes and no wire message changes, so this recommendation should name the shared config schema/type rather than imply a wire-protocol version change.

A diagnostic-owned open apron can be implemented in the isolated worker test path only after its geometry and limits are authorized. The existing value `325` is currently part of the direct-shot guard and is not automatically transferable to a different start-state/matrix merely because it is numerically the needed extent. The public shape APIs establish capability, not a safe support proof. No source run, browser run, app check, or physics simulation was performed for this review; no runtime, clearance, or gameplay conclusion follows.
