## Required behavior

- Create stable identity and opaque random session; store only SHA-256 digests; cookie only for session, never response JSON. `GET /session` restores identity. Logout validates CSRF and revokes. Username alone cannot resume/authenticate.
- Optional high-entropy recovery code is returned only at issuance. Recovery request includes both username and code, compares the expected normalized username within the same DB transaction before consuming the code, revokes old sessions, and issues fresh session/recovery credentials. All invalid recovery cases return the same public failure.
- Mutations require exact configured Origin, `application/json`, an exact allow-listed object shape, and a 4 KiB request cap. Return bounded actionable errors without secrets.
- Production cookie name/options follow PLATFORM (`__Host-korre_session; HttpOnly; Secure; SameSite=Lax; Path=/; no Domain`). Development may use an explicitly named insecure localhost-only cookie; composition must never select it in production.
- CSRF token is bound to the opaque session using HMAC and a configured secret; keep session/CSRF secrets out of logs and response headers. Return CSRF only to the same-origin identity client, never store credentials in localStorage.
- Use repository-backed atomic limits: five registration attempts/hour per IP; five recovery attempts/hour per IP and normalized username. Store only keyed HMAC buckets, not raw address or username; prune expired buckets in bounded batches. Limits are operational defaults, not cultural rules.
- Route construction accepts repository/service/config/address lookup dependencies; it does not mount itself or read deployment secrets from globals. Coordinator will wire it into `app.ts` and `index.ts`.
